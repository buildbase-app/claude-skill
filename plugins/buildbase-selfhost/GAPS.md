## Priority 1 - data-loss / correctness risk

### 1. Backup & restore procedure (narrowed)
- **Partly closed.** The production page's Updating section now says to back up MongoDB first, with `mongodump` against `MONGO_CONNECTION_URL`.
- **Still missing:** the `mongodump` flags, a schedule, off-host storage, any restore procedure, Redis backup, and backing up the GCS bucket that holds uploaded files.
- **Why it matters:** the central server holds no copy of customer data; if the operator has no backup, there is no recovery path.
- **Skill file affected:** `knowledge/operations/upgrades-backups.md`.

### 2. `DB_ENCRYPTION_KEY` lifecycle
- **What's missing:** the config table defines it as "Database field encryption key" and nothing more. Unspecified: can it be rotated? What happens to existing encrypted data if it changes? Does a restore require the *original* key?
- **Why it matters:** if changing the key silently makes existing data unreadable, an operator can destroy their data without warning.
- **Skill file affected:** `knowledge/config/env-reference.md`, `knowledge/operations/upgrades-backups.md`.

### 3. Secret-rotation consequences
- **What's missing:** effects of rotating `JWT_PASS`, `OAUTH2_SECRET`, `SECRET_KEY` (forced re-auth? token/session invalidation? safe or not?).
- **Now documented, and excluded from this row:** regenerating the Installation API key keeps the old key working for up to 60 minutes; `BULLMQ_DASHBOARD_PASSWORD` exists so the job-dashboard password and the installation key can be rotated apart; `MAIL_TRACKING_SECRET` makes the tracking key independent of `JWT_PASS`.
- **Skill file affected:** `knowledge/config/env-reference.md`.

## Priority 2 - operability

### 4. Activation / licensing & central-server connectivity failure states (closed, one detail open)
- **Closed.** The overview's "Licensing and the connection to BuildBase" table documents each state: missing installation variables (the tenant server does not start and names the variable), a wrong or regenerated key (end users unaffected; the installation shows disconnected and logs `[CentralAPI] central refused ...`), BuildBase unreachable (end users unaffected; console sign-in waits), and a lapsed self-hosting plan. It also documents the five-minute status check-in and the console's minimum-version gate.
- **Still open:** the exact outbound host and port to allow. `central.console.buildbase.app` still appears only as a label in `configuration.mdx`'s diagram.
- **Skill file affected:** `knowledge/mental-models/installations.md`, `knowledge/failure-library/selfhost-mistakes.md`.

### 5. External MongoDB connection details (narrowed)
- **Partly closed.** The template ships an Atlas-style example, `MONGO_CONNECTION_URL=mongodb+srv://user:password@your-cluster.mongodb.net/`, with the warning that omitting it leaves the server on localhost and never ready.
- **Still missing:** TLS, `replicaSet` and `authSource` parameters, and any guidance for a self-managed replica set.
- **Skill file affected:** `knowledge/config/env-reference.md`, `knowledge/deploy/production.md`.

### 6. Image tags, upgrades & rollback (narrowed)
- **Partly closed.** The update procedure is documented (back up, save the release's compose file over yours, pull, `up -d`), the tenant server runs pending migrations at boot and logs a summary line, manual migrations are listed and run by name with `node build/migrations/run.js`, and a version is pinned by replacing `latest` in the three `image:` lines (the repo's compose uses `IMAGE_TAG`). The pre-release-23 `CHOWN` crash loop and its recovery are documented.
- **Still missing:** a list of published tags, a rollback procedure, and whether running an older image after a newer one migrated the database is safe.
- **Skill file affected:** `knowledge/operations/upgrades-backups.md`.

### 7. Logs & monitoring (closed)
- **Closed.** `GET /api/ready` and `GET /api/health` now have documented payloads and status codes (the full health report needs `x-internal-api-key: <INSTALLATION_API_KEY>`), with `READINESS_REDIS_FAIL_OPEN` for a Redis outage. `LOG_LEVEL` is documented, the six `NEW_RELIC_*` variables point at the operator's own account, and every compose service has `logging: json-file` with size caps, so `docker compose logs <service>` is the log path.
- **Skill file affected:** `knowledge/deploy/production.md`, `knowledge/operations/upgrades-backups.md`.

### 11. TLS termination topology
- **What's missing:** production tells the operator to run `certbot --nginx`, which configures an Nginx on the host, while the compose's own Nginx listens on plain HTTP (8080 in the container, published on `TENANT_SERVER_PORT`) with a read-only config mount. How the two are meant to fit together, and what `TRUST_PROXY` should then be, is never described.
- **Skill file affected:** `knowledge/deploy/production.md` (currently flags this inline).

## Priority 3 - completeness

### 8. Optional-service setup walkthroughs (narrowed)
- **Partly closed.** The configuration table now spells out what the staging and exports buckets need (location, lifecycle rules, CORS, public access prevention, signing credentials), and what each sign-in, URL-safety, commerce and storage switch does by default.
- **Still missing:** a walkthrough for `GOOGLE_AUTH_CLIENT_ID/SECRET`, the GCS service account and its IAM, the Pub/Sub finalize notification, the six `NEW_RELIC_*` variables, Turnstile keys, and a ClamAV deployment beyond the compose's optional `scanner` profile. `MAILGUN_API_KEY` is gone from the docs: each organization's email goes through its own sender set in the console.
- **Skill file affected:** `knowledge/config/env-reference.md`.

### 9. Scaling beyond the fixed 2 replicas
- **What's missing:** the production compose hard-codes `replicas: 2`; no guidance on scaling further, or on sizing MongoDB/Redis for load. (The Nginx upstream is now sticky by client address for socket.io, and the workers run in every replica; neither is a scaling guide.)
- **Skill file affected:** `knowledge/deploy/production.md`.

### 10. Decommission / data export (narrowed)
- **Partly closed.** Deleting an installation stops its key at once and unassigns its organizations without deleting their data; an organization owner's data export is written to `EXPORTS_BUCKET` (off when unset); assigning an organization to an installation on a different MongoDB starts it without its data "until you migrate it".
- **Still missing:** how to migrate an organization's data between installations, and how to tear a stack down and keep or hand over its data.
- **Skill file affected:** `knowledge/mental-models/installations.md`, `knowledge/operations/upgrades-backups.md`.

## How the skill handles these today

Every file in `knowledge/` is grounded only in the sources above. Where a topic above arises, the skill is instructed (in `SKILL.md` -> "What not to do" and per-file "not documented" notes) to say it isn't in the current self-hosted docs and point to [docs.buildbase.app/self-hosted](https://docs.buildbase.app/self-hosted/overview) - **never to invent a procedure.**
